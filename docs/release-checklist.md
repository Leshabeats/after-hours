# Проверка выпуска публичных исследований

Приёмка [#12](https://github.com/Leshabeats/after-hours/issues/12). Подготовка и проверки не означают публикацию сайта или закрытие задачи.

## GitHub OAuth

1. Выбрать доступный из браузера адрес сайта. Для запуска на своём компьютере подойдёт `http://127.0.0.1:5173`; loopback облачного контейнера не является адресом сайта на компьютере пользователя.
2. Создать OAuth App в [GitHub Developer settings](https://github.com/settings/developers). Homepage URL — выбранный origin, Authorization callback URL — тот же origin с `/api/auth/callback`.
3. Сохранить `GITHUB_CLIENT_ID` и `GITHUB_CLIENT_SECRET` в защищённом окружении сервера. Установить `APP_ORIGIN` без пути, например `https://after-hours.example`. Перезапустить сервер после изменения окружения.
4. В production задать постоянный случайный `AUTH_SECRET` длиной не менее 32 байт. Его замена завершает существующие сессии. GitHub access token используется при входе и не сохраняется в базе.
5. Открыть `/log`, войти, проверить логин, журнал и выдачу доступа коннектору. Повторить со вторым аккаунтом. Проверка перенаправления без завершения входа не считается пройденным OAuth.

Для анонимного режима OAuth не обязателен. Сеть сервера должна разрешать HTTPS к `github.com` (обмен OAuth-кода) и `api.github.com` (пользователь, каталог, история). В среде с HTTP-прокси сохранять его настройки и доверенные CA; для Node 22 включить `NODE_USE_ENV_PROXY=1`.

## Автоматические проверки

Запустить `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`, затем `npm run test:production`. CI выполняет тот же набор.

Smoke запускает собранный Node-сервер на свободном loopback-порту, использует отдельную временную SQLite и синтетические подписанные сессии. Сетевые чтения сервера отключены тестовым preload-модулем; модель и реальный OAuth не вызываются. Проверяются:

- Главная, каталог, журнал, отказ анонимным запросам и неверному OAuth state.
- Дополнение базы с существующим журналом и расходом новыми таблицами исследований без потери старых записей.
- Доставка через настоящий `/api/research`, отчёт в HTML задачи и профиля, изоляция владельцев и отсутствие частных лимитов в публичном HTML.
- Повторная доставка после потерянного ответа, остановка сервера, отдельный процесс коннектора `--flush-only`, сохранение очереди и доставка после рестарта без двойного расхода.
- Перезапуск из другого рабочего каталога с тем же абсолютным `DATA_DIR`.
- Неуспешные/ожидающие исследования без ложной публикации, снятие публикации в обоих представлениях, отзыв доступа и целостность SQLite.

При успехе временные данные удаляются. При ошибке smoke выводит путь к сохранённым локальным логам и тестовой базе; это не пользовательская база. Браузерные действия и настоящий Codex проверяются отдельно.

## Сквозной запуск

Использовать контролируемый публичный репозиторий. Для проверки уже существующего PR достаточно чтения; создание комментария, PR или ревью — отдельная внешняя запись.

1. Войти через GitHub, выбрать задачу вручную, затем через рандом. Проверить, что Codex-ссылка содержит правильную задачу.
2. На `/log` выдать доступ и запустить [локальный коннектор](research-connector.md). Зафиксировать версию CLI и итоговый статус, не копируя токен доступа, cookie или полный stderr в отчёт.
3. После завершения проверить отчёт на `/m/owner/repo/number` и `/u/login`. Сверить каждый ход с `thread/tokenUsage/updated.last`: накопительный `total` не прибавлять, cached input повторно не учитывать. Неизвестный расход не заменять нулём.
4. Отдельно сверить приватные лимиты и время сброса с `account/rateLimits/read`; отсутствие доступного лимита отметить как отсутствие данных.
5. Повторить исследование той же задачи: новый запуск, правильный автор, история и сумма. Прервать ещё один запуск или дождаться запроса к человеку: он не должен публиковаться как завершённый.
6. Остановить доставку перед завершением, перезапустить коннектор и восстановить сервер: отчёт и расход должны записаться ровно один раз.
7. Проверить второй аккаунт: он не может изменить чужую публикацию или доступ и не видит чужие частные лимиты. Снять отчёт с публикации и проверить задачу и профиль в отдельном анонимном браузере.
8. Привязать существующий публичный PR в контролируемом репозитории, проверить историю GitHub. Не путать завершение исследования, merge PR и исправление issue.

## Постоянные данные, обновление и откат

Использовать один Node-процесс и абсолютный `DATA_DIR` на постоянном локальном диске, доступном пользователю процесса. Не хранить рабочую SQLite внутри заменяемого каталога релиза. По умолчанию используется `./data`, поэтому для существующей установки сначала определить фактическое расположение базы.

Перед обновлением остановить сервер и сделать резервную копию всего каталога данных. Копировать работающую SQLite обычным `cp` небезопасно; при остановленном процессе сохраняются и возможные служебные файлы журнала. Хранить `AUTH_SECRET` отдельно в защищённой конфигурации. При переносе development-установки сохранять также `DATA_DIR/.auth-secret`.

Текущая инициализация схемы добавляет таблицы/индексы через `CREATE ... IF NOT EXISTS`. Это не механизм произвольной миграции столбцов: будущие изменения схемы требуют отдельной миграции и проверки на копии базы. После запуска нового релиза проверить журнал, авторизацию, отчёты и `PRAGMA integrity_check` на базе.

Для отката остановить сервер, сохранить проблемную базу для разбора, вернуть предыдущую версию приложения и соответствующую резервную копию данных. Восстановление старой копии потеряет записи, поступившие после неё; согласовать это до отката. Не откатывать схему автоматически при старте.

Перед выпуском отдельно записать результаты локальных проверок, реального OAuth/Codex, CI и ревью итогового коммита. Merge и deployment имеют собственные статусы. Непройденный реальный вход или запуск модели оставляет #12 открытой.
