# Проверка выпуска публичных исследований

Приёмка [#12](https://github.com/Leshabeats/after-hours/issues/12). Подготовка и проверки не означают публикацию сайта или закрытие задачи.

## GitHub OAuth

1. Сохранить существующий локальный OAuth App: Homepage `http://127.0.0.1:5173`, callback `http://127.0.0.1:5173/api/auth/callback`. Для production выбрать реальный HTTPS-адрес Vercel/домена; loopback облачного контейнера не является адресом сайта на компьютере пользователя.
2. Создать отдельный production OAuth App в [GitHub Developer settings](https://github.com/settings/developers). Homepage URL — выбранный origin, Authorization callback URL — тот же origin с `/api/auth/callback`.
3. Сохранить `GITHUB_CLIENT_ID` и `GITHUB_CLIENT_SECRET` в защищённом окружении сервера. Установить `APP_ORIGIN` без пути, например `https://after-hours.example`. Перезапустить сервер после изменения окружения.
4. В production задать постоянный случайный `AUTH_SECRET` длиной не менее 32 байт. Его замена завершает существующие сессии. GitHub access token используется при входе и не сохраняется в базе.
5. Открыть `/log`, войти, проверить логин, журнал и выдачу доступа коннектору. Повторить со вторым аккаунтом. Проверка перенаправления без завершения входа не считается пройденным OAuth.

Vercel Preview использует development-ветку Neon, отдельный `AUTH_SECRET` и пустые OAuth credentials; `VERCEL_ENV=preview` дополнительно запрещает вход. Для анонимного режима OAuth не обязателен. Сеть сервера должна разрешать HTTPS к `github.com` (обмен OAuth-кода) и `api.github.com` (пользователь, каталог, история). В среде с HTTP-прокси сохранять его настройки и доверенные CA; для Node 22 включить `NODE_USE_ENV_PROXY=1`.

## Автоматические проверки

Использовать Node 22 / npm 11 (`npm install -g npm@11`, затем `npm ci`). Запустить `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`, затем `npm run test:production` и `npm run build:vercel`. CI выполняет этот набор с PostgreSQL 17 service и без Neon secrets.

Для PostgreSQL-проверок экспортировать `TEST_DATABASE_URL`, указывающий на отдельную ephemeral PostgreSQL 17 на localhost с именем базы `*_test`. Ни тесты, ни smoke не читают `.env.local` и не используют рабочий `DATABASE_URL`. Каждый прогон создаёт и удаляет случайную схему. Без тестового URL DB-контракты пропускаются, smoke отказывается запускаться. Локальная разработка приложения использует Neon development и не требует Docker; ephemeral PostgreSQL нужен только для локального воспроизведения DB-проверок, которые также выполняет CI.

Smoke запускает собранный Node-сервер на свободном loopback-порту с синтетическими сессиями. Внешние сетевые чтения сервера отключены тестовым preload-модулем; модель и реальный OAuth не вызываются. Проверяются:

- Главная, каталог, журнал, отказ анонимным запросам и неверному OAuth state.
- Существующий журнал и расход в PostgreSQL сохраняются при запуске и перезапуске сервера.
- Доставка через настоящий `/api/research`, отчёт в HTML задачи и профиля, изоляция владельцев и отсутствие частных лимитов в публичном HTML.
- Повторная доставка после потерянного ответа, остановка сервера, процесс коннектора `--flush-only`, очередь и доставка после рестарта без двойного расхода.
- Перезапуск из другого рабочего каталога с той же PostgreSQL.
- Ожидающие/прерванные исследования без ложной публикации, снятие публикации в обоих представлениях и отзыв доступа.

При ошибке smoke сохраняет локальные логи и очередь по выведенному пути; тестовая схема всё равно удаляется. Браузерные действия и настоящий Codex проверяются отдельно. Отдельные DB-тесты проверяют параллельные импорты/мутации журнала, первые записи и replay исследований, сохранение ходов, rollback, дедупликацию GitHub subjects/facts и общий rate-limit pause.

## Сквозной запуск

Использовать контролируемый публичный репозиторий. Для проверки уже существующего PR достаточно чтения; создание комментария, PR или ревью — отдельная внешняя запись.

1. Войти через GitHub, выбрать задачу вручную, затем через рандом. Проверить, что Codex-ссылка содержит правильную задачу.
2. На `/log` выдать доступ и запустить [локальный коннектор](research-connector.md). Зафиксировать версию CLI и итоговый статус, не копируя токен доступа, cookie или полный stderr в отчёт.
3. После завершения проверить отчёт на `/m/owner/repo/number` и `/u/login`. Сверить каждый ход с `thread/tokenUsage/updated.last`: накопительный `total` не прибавлять, cached input повторно не учитывать. Неизвестный расход не заменять нулём.
4. Отдельно сверить приватные лимиты и время сброса с `account/rateLimits/read`; отсутствие доступного лимита отметить как отсутствие данных.
5. Повторить исследование той же задачи: новый запуск, правильный автор, история и сумма. Прервать ещё один запуск или дождаться запроса к человеку: он не должен публиковаться как завершённый.
6. Остановить доставку перед завершением, перезапустить коннектор и восстановить сервер: отчёт и расход должны записаться ровно один раз.
7. Проверить второй аккаунт: он не может изменить чужую публикацию или доступ и не видит чужие частные лимиты. Снять отчёт с публикации и проверить задачу и профиль в отдельном анонимном браузере.
8. Привязать существующий публичный PR в контролируемом репозитории, проверить историю GitHub. Не путать завершение исследования, merge PR и исправление issue.

## Vercel, миграции, backup и откат

1. Создать отдельный проект на **Neon Free**, регион Frankfurt (`eu-central-1`), и разместить Vercel Functions во Frankfurt (`fra1`). Существующие ресурсы Velora не менять. Если Free недоступен, не переходить на платный план автоматически: это требует отдельного решения. Инструкция не означает, что ресурсы уже созданы. Создать пустую Neon production-ветку и отдельную development-ветку. Историческая SQLite не переносится. Локальная `.env.local` содержит только development URLs. Runtime `DATABASE_URL` — pooled, `DATABASE_URL_UNPOOLED` — direct той же ветки.
2. В Vercel Production установить URLs production-ветки, `AUTH_SECRET`, `APP_ORIGIN`, credentials production OAuth App и при необходимости `GITHUB_TOKEN`. Preview получает development URLs и отключённый OAuth. Оба окружения используют Node 22 / npm 11; `vercel.json` задаёт `npm run build:vercel`.
3. До направления трафика применить `npm run db:migrate` с direct URL целевой ветки. Команда явно читает `.env.local`; переданные переменные процесса имеют приоритет. Сверить целевую ветку в Neon до запуска. Никогда не добавлять migrations в HTTP path или Preview build.
4. Версионные SQL-файлы в `migrations/` применяются одной транзакцией с advisory lock. Таблица `schema_migrations` хранит checksum: применённые файлы не редактировать, новое изменение — новый файл. Совместимые изменения схемы выпускаются до кода, удаление старых колонок — отдельным поздним выпуском.
5. До production-изменений зафиксировать Neon restore point/backup согласно доступному плану и проверить способ восстановления в отдельную ветку. Хранить `AUTH_SECRET` в защищённой конфигурации: его замена завершает сессии. Persistent filesystem для приложения не нужен.
6. После deployment проверить страницы, журнал, выдачу доступа, реальный OAuth и Desktop Codex. При проблеме кода вернуть предыдущий совместимый Vercel deployment. Схему автоматически не откатывать. Для восстановления данных создать/проверить восстановленную Neon-ветку и переключить URLs только после оценки записей, поступивших после restore point; восстановление старой копии может их потерять.

Перед выпуском отдельно записать результаты локальных проверок, реального OAuth/Codex, CI и ревью итогового коммита. Merge и deployment имеют собственные статусы. Непройденный реальный вход или запуск модели оставляет #12 открытой.
